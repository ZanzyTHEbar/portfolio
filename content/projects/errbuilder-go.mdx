## Strange Idea

Project errors can use one builder with meaningful codes.

## Hypothesis

A single Builder with a gRPC-inspired code set, an error map for complex flows, and structured details can keep error handling uniform across projects.

## Constraints

- general-purpose: usable in any Go project
- codes need standardized meaning, not per-call-site invention
- deferred and multi-error flows must fit the same shape

## System

Packages can define different error shapes and call-site codes. errbuilder-go is a lightweight custom error-builder library for Go. Its Builder constructs errors with a message, code, and details. `ErrMap` collects errors across complex or deferred flows. Builtin wrappers demonstrate common usage.

## Reality

The open-source Go module was originally built for the author's own projects and then generalized. It pairs with assert-lib.

## Open Questions

- README install/usage snippets use `errorbuilder` and `errsx` import paths that do not match the module name. Which path is canonical?
- Are the 5 builtin wrappers in `errors.go` enough, or does every new project grow its own set anyway?
- Does `ErrMap` actually cover deferred/multi-error flows in practice, or do callers bypass it?
