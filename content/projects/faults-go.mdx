## Strange Idea

Each application fault carries a stable fault code and a transport code.

## Hypothesis

Across process boundaries, wrapped Go faults expose a stable application code alongside its mapped transport code for inspection.

## Constraints

- stdlib compatibility (`errors.Is` / `errors.As` must keep working)
- context cancellation and deadline semantics
- Process-wide code mappings and their global state

## System

faults-go is a Go library for structured application faults. `New` and `Wrap` create and wrap faults with normalized key/value details. `CodeOf` and `IsCode` inspect codes. Process-wide registration maps application codes to transport codes. The library builds on errbuilder-go for transport-aware error values and integrates assert-lib reporting.

## Reality

The open-source Go module has CI, Go Reference documentation, and an MIT license. It is part of a three-library set with errbuilder-go and assert-lib.

## Decisions

- Durable application codes and transport codes remain separate.
- The library builds on errbuilder-go and assert-lib.

## Open Questions

- Process-wide code-to-transport registration uses global state; its behavior for multi-package callers needs testing.
- The three-module boundary among faults-go, errbuilder-go, and assert-lib needs a long-term decision.
- Fault-code reuse beyond validation and database examples needs documented guidance.
