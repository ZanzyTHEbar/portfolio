## Strange Idea

Each application fault carries a stable fault code and a transport code.

## Hypothesis

Durable application codes such as `validation.failed` and transport codes such as `InvalidArgument` can keep errors structured across process boundaries.

## Constraints

- stdlib compatibility (`errors.Is` / `errors.As` must keep working)
- context cancellation and deadline semantics
- process-wide code mappings without global-state surprises

## System

Error strings alone do not provide stable matching, translation, or boundary mapping. faults-go is a small Go library for stable, structured application faults. `New` and `Wrap` create and wrap faults with normalized key/value details. `CodeOf` and `IsCode` inspect codes. Process-wide registration maps application codes to transport codes. The library builds on errbuilder-go for transport-aware error values and integrates assert-lib reporting.

## Reality

The open-source Go module has CI, Go Reference docs, and an MIT license. It is part of a three-library set with errbuilder-go and assert-lib.

## Decisions

- Durable application codes and transport codes remain separate.
- The library builds on errbuilder-go and assert-lib.

## Open Questions

- Process-wide code-to-transport registration uses global state. Where does it surprise multi-package callers?
- faults-go wraps errbuilder-go and reports via assert-lib. Does the trio stay three modules or collapse into one?
- Beyond validation/database examples, which fault codes actually get reused across projects?
